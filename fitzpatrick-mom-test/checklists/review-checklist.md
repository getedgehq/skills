# Review checklist

Mark each applicable gate **PASS** or **FAIL**, with a brief evidence location or repair. Use **N/A** only with a reason. These gates are package adaptations of the cited principles, not a numerical validation score. A finished draft with unresolved failures should state its limitations and proposed repair.

## Pass/fail gates

- [ ] **Purpose:** A customer group, product stage, deliverable mode, and concrete decision are stated.
- [ ] **Goal:** Learning and selling outcomes are distinguished; a mixed guide makes the transition explicit. [S2]
- [ ] **Objectives:** Three prioritized learning objectives address uncertainty rather than collect endorsement. At least one could undermine the plan. [S4] [S5]
- [ ] **Participants:** Relevant experience, access route, relationship, and any unknown buying role are visible. Friendly first contacts are not treated as representative demand. [S6]
- [ ] **Questions:** Discovery questions focus on the person's life and specific past episodes, with brief conditional probes that allow listening. [S3]
- [ ] **Workflow:** The output seeks or records what happened and why, including tools, effort, alternatives, and outcome. Manual work is not automatically labeled a software need. [S3] [S4]
- [ ] **Contamination:** Praise, forecasts, and reactions after a pitch are identified rather than counted as adoption evidence. [S5]
- [ ] **Features:** Feature requests are separated from the desired result and current workaround. Even paying customers' proposals receive investigation. [S5]
- [ ] **Fit:** The proposed intervention identifies its boundary, surrounding tools, and required habit changes. Problem importance and solution adoption are separate hypotheses. [S7]
- [ ] **Next evidence:** The next experiment matches the uncertainty. Experience-dependent value receives a prototype or observable use task when appropriate. [S4] [S6]
- [ ] **Commitment:** When an offer exists, the ask is specific and meaningful. Requested, agreed, completed, and declined actions remain distinct; purchasing progress is not inferred from friendly meetings. [S2] [S4]
- [ ] **Traceability:** Customer claims point to supplied notes or observations. Method citations support the procedure only. Missing findings remain unknown and illustrations remain labeled invented.
- [ ] **Decision:** The recommendation shows supporting facts, contrary facts, remaining uncertainty, changed understanding, and a next action. It does not claim perfect certainty. [S6] [S8]

## Common failure modes and repairs

| Failure | Repair |
| --- | --- |
| Approval questionnaire | Replace idea judgments with the latest relevant episode and specific follow-ups. [S3] |
| Hypothetical price treated as revenue evidence | Explore actual comparable spending; when an honest offer exists, ask for an appropriate buying action. [S3] [S4] |
| Polite praise labeled validation | Mark it as opinion; return to behavior or make a concrete sales ask. [S5] |
| Interviewer pitches after every answer | Shorten prompts and listen; record the pitch boundary and contaminated reactions. [S3] [S5] |
| Feature requests become the roadmap | Investigate the triggering event, underlying result, and workaround first. [S5] |
| Untidy tools imply replacement demand | Learn why the current tools fit before changing the workflow. [S4] [S7] |
| Strong pain treated as proof of solution fit | Identify required behavior changes and test the proposed intervention separately. [S7] |
| More meetings substitute for sales progress | Ask for a meaningful next step and record whether it occurred. [S2] [S4] |
| A booked session is reported as completed testing | Record agreed time separately; update only when the session occurs. |
| A refusal is treated as a universal rejection | Investigate timing, role, constraints, and offer fit; limit the conclusion to the evidence. [S4] |
| Abstract interviews continue for an experience-led product | Put an appropriate prototype into users' hands and examine actual use. [S4] [S6] |
| Improved questions are presented as new findings | Preserve the original record; label rewrites as future questions and gaps as unknown. |
| Neat notes contain no decision implication | Explain what changed and which next action addresses the remaining risk. Reflection is adapted from [S8]. |

## Completion rule

Repair failures that can be fixed from available inputs. If a failure requires new customer evidence, identify the precise missing fact and prepare a follow-up instead of inventing a pass. Deliver a bounded conclusion supported by the existing record, together with the next useful test. Do not contact participants or make commercial commitments merely because the brief recommends them.
