# Pre-registration, sample size for the 2026-09-17 wave

Written 2026-09-17, before any aggregate for these runs existed. At the moment of
writing, `results/t2-v2/summary.json` and `results/bf-v1/summary.json` did not
exist and no judge output from either run had been read.

## The decision

Every skill in this wave is run at **6 samples per task per arm**, giving 18
judged pairs per arm. This applies to:

- `bf-v1`: cli-ux-review, http-error-triage, people-search, linkedin-media-prep
- `t2-v2`: shadcn-first, security-audit-checklist
- `new-v1`: generate-image, cv-job-match, pay-per-call-apis, product-launch-video

`bf-v1` and `t2-v2` were started at 3 samples. They are topped up to 6 by a
second batch launched only after the 3-sample processes exit, because the batch
runner computes its job list once at startup and does not lock per attempt, so a
concurrent process on the same task set would duplicate in-flight attempts.

## Why this is not optional stopping

Raising n after seeing a positive estimate inflates the false positive rate. The
protection is that n was fixed here, in writing, before any of these numbers were
computed or read. The resolution rule is unchanged and remains: a cell is
resolved only if the 95% confidence interval on the judge point delta excludes
zero.

If a top-up cannot complete for a given skill, the published figure is the
smaller n with the shortfall stated, not a figure chosen for its value.

## Addendum, 2026-09-17, later the same day

Appended rather than edited, because a pre-registration that can be rewritten is
not one. Nothing above changed.

Two things happened after this was written, and both are changes to how the rule
above is computed, not to the rule itself.

The 95% interval is now a two-sided t interval on the per-task means. It was a
percentile cluster bootstrap, which we measured against a known truth and found
anti-conservative at the task counts this wave runs: at a true effect of exactly
zero it excludes zero about 15.7% of the time at 3 tasks. Every figure this
benchmark had computed was re-read against the corrected interval before this
wave landed, so the wave is read off the same estimator from its first aggregate
onward. `docs/BENCHMARK.md` sections 5 and 11 have the measurement and the sweep.

The win rate no longer resolves anything and no longer carries an interval. The
rule above already keyed resolution to the judge point delta, so this changes no
verdict in this wave; it removes a second label the harness used to print beside
each cell, computed as a t interval on a quantity bounded in [0, 100], which at
3 tasks produced bounds above 100 and below 0. A bounded replacement will be
pre-registered before the next wave rather than chosen after seeing which cells
it would move.

One thing this addendum cannot undo: 6 samples per task was the wrong lever, and
we know that now. The shortfall in the old interval lives in the task count, and
our own power simulation says 3 to 6 samples at 3 tasks moves power on a 5 point
effect from 0.14 to 0.16, while 3 to 6 tasks at 3 samples moves it from 0.14 to
0.38. This wave still runs at 6 samples and 3 tasks, as registered, because
changing n mid-wave after seeing that argument is exactly what a pre-registration
exists to prevent. Six tasks per skill is the binding requirement for the next
one.
